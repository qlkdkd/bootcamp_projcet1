## 3. 핵심 설계 결정 6가지 (왜 이렇게 만들었나)

발표에서 "구조를 설명하라"는 질문에 이 6가지를 말하면 됩니다.

1. **집계와 입출력을 분리했다.**
   `analysis.py`는 DataFrame을 받아 DataFrame을 돌려줄 뿐 파일을 전혀 건드리지 않습니다.
   그래서 같은 함수를 `main.py`는 파일로 저장하는 데, `app.py`는 화면에 보여 주는 데 씁니다. (S1, D7)

2. **불량률 계산을 한 곳에 모았다.**
   `_rate_table` 함수 하나가 "묶고 → 세고 → 불량률 계산"을 합니다.
   시설별(F4), 날짜·시설별(F6), 카메라별(F7)은 묶는 기준만 다르게 넘깁니다.
   계산 방식이 세 군데서 달라질 일이 없습니다.

3. **"불량"의 정의도 한 곳에 모았다.**
   `defect_mask`가 `result == "NG"`인지 판단합니다. 불량 종류 조건이 있으면 그것도 여기서 처리합니다.
   모든 집계가 이 함수를 쓰므로, 정의를 바꾸려면 이 함수만 고치면 됩니다.

4. **파일 이름, 경로, 기준값을 코드에 적지 않았다.**
   파일은 `glob("facility_*.csv")`로 찾습니다(F1).
   경로와 기준값은 "기본값 ← config.json ← 명령 인자" 순서로 받습니다(S2).

5. **문제가 있는 파일은 멈추지 않고 건너뛴다.**
   파일 하나를 `read_log_file`로 읽다가 문제가 생기면 `None`을 돌려주고, 이유를 `run_log.txt`에 남깁니다(S4).

6. **Dash는 시작할 때 한 번만 읽고, 콜백 하나로 전부 다시 계산한다.**
   로그는 `app.py` 최상단에서 읽어 `DF`에 둡니다.
   선택 4개(시설, 시작일, 종료일, 불량 종류)를 Input으로 받는 `update` 함수 하나가 카드·그래프·표 17개를 모두 돌려줍니다(D6, D7).

## 6. 예상 질문과 답

### 구조

**Q. 함수를 왜 이렇게 여러 파일로 나눴나요?**
역할별로 나누면 수정할 곳이 분명해집니다. 저장 방식을 바꾸려면 `writer.py`만, 집계 기준을 바꾸려면 `analysis.py`만 고치면 됩니다. 특히 집계 함수가 파일 입출력을 하지 않으므로 처리 프로그램과 Dash가 같은 함수를 함께 쓸 수 있습니다.

**Q. Dash 파일에 집계 코드가 없다는 걸 어떻게 보장하나요? (D7)**
`app.py`의 `update` 함수는 `analysis.filter_records`, `facility_summary`, `facility_defect_table`, `daily_facility_summary`, `find_anomalies` 같은 모듈 함수만 부릅니다. app.py 안의 `melt`와 `to_table`은 집계가 아닙니다. 이미 집계된 표를 그래프와 표 부품이 받는 형식으로 모양만 바꾸는 코드입니다.

**Q. 로그를 한 번만 읽는다는 건 어디서 보이나요? (D7)**
`app.py` 35번째 줄 `DF, CODES = loader.load_dataset(CONFIG)`가 함수 밖, 즉 파일을 실행할 때 한 번만 실행되는 위치에 있습니다. 콜백은 이 `DF`만 사용합니다. 또 `debug=False`로 실행해 자동 재시작으로 두 번 읽는 일을 막았습니다.

### 계산

**Q. 판정 불가(D99)도 불량에 넣었나요?**
네. 로그에서 D99의 `result`가 NG이므로, "불량 = NG"라는 하나의 기준으로 셌습니다. 대신 D99는 F8 이상 기록에 따로 모아서 실제 제품 불량과 구분해 볼 수 있게 했습니다.

**Q. 합계 행의 불량률은 어떻게 계산했나요?**
시설별 불량률의 평균이 아니라 `전체 불량 수 / 전체 검사 수`로 다시 계산했습니다. 시설마다 검사 수가 다르므로 평균을 내면 틀립니다. 실제로 (5.14 + 4.14 + 4.31) / 3 = 4.53%이지만, 정답은 238 / 5,198 = 4.58%입니다.

**Q. Dash에서 불량 종류를 고르면 불량률이 어떻게 되나요?**
검사 수는 시설·날짜 조건으로만 정하고, 불량 수는 고른 종류만 셉니다. 행 자체를 불량 종류로 거르면 남은 행이 전부 불량이라 불량률이 항상 100%가 되기 때문입니다.

**Q. 날짜 범위의 끝 날짜는 포함되나요?**
네. `timestamp < 끝 날짜 + 1일`로 비교합니다. `<= 끝 날짜`로 하면 그날 00:00:00까지만 포함되어 하루치가 빠집니다.

### 예외 처리

**Q. 파일에 문제가 있으면 어떻게 되나요? (S4)**
`read_log_file`이 두 가지를 검사합니다.
1. 읽기 자체가 실패하면(인코딩 오류, 빈 파일 등) `try/except`로 잡습니다.
2. 필요한 14개 열 중 빠진 열이 있는지 검사합니다.

문제가 있으면 `None`을 돌려주고 경고를 `run_log.txt`에 남깁니다. `read_all_logs`가 `None`을 빼고 모으므로 나머지 파일로 처리를 계속합니다. 깨진 파일 3개를 넣어 직접 테스트했습니다.

**Q. 불량코드표가 없으면요?**
불량코드표는 건너뛰지 않고 오류로 처리합니다. 불량 이름과 분류가 없으면 F3, F5를 만들 수 없기 때문입니다. 이 오류는 `main()`의 `try/except`가 잡아 실행 로그에 남기고 종료 코드 1로 끝냅니다.

**Q. 엑셀에서 한글이 안 깨지는 이유는요? (S5)**
CSV를 `utf-8-sig`로 저장해 파일 맨 앞에 BOM이 붙기 때문입니다. 엑셀은 BOM을 보고 UTF-8로 읽습니다. BOM 없는 UTF-8로 저장하면 엑셀이 한국어 Windows 인코딩(CP949)으로 읽어서 깨집니다.

**Q. 그래프 한글이 안 깨지는 이유는요? (F10)**
matplotlib의 기본 글꼴에는 한글이 없습니다. 그래서 `set_korean_font`가 설치된 한글 글꼴을 찾아 지정합니다. 이때 `axes.unicode_minus=False`도 함께 설정해 마이너스 기호가 네모로 깨지는 것을 막습니다.

### 선택 요구사항

**Q. 급증은 무엇을 기준으로 판단했나요? (O2)**
날짜·시설·카메라 단위로, 세 조건을 모두 만족하면 급증입니다.
1. 그날 불량이 5건 이상 → 건수가 적은 우연한 변동은 제외
2. 그날 불량률이 평소의 2배 이상 → 평소는 같은 카메라의 **그날을 뺀** 나머지 날 불량률
3. z 점수가 3 이상 → 이항분포로 봤을 때 우연이라 보기 어려운 차이

그날을 빼는 이유는, 그날 값이 평소 값에 섞이면 급증이 작게 보이기 때문입니다.

**Q. z 점수가 뭔가요?**
"이 차이가 우연한 흔들림의 몇 배인가"입니다.
- 평소 불량률이 p0일 때 n건을 검사하면, 불량률은 보통 `√(p0(1−p0)/n)` 정도 흔들립니다(표준오차).
- 실제 차이 `(p − p0)`를 이 값으로 나눈 것이 z입니다.
- z가 3 이상이면 우연히 이 정도 차이가 날 확률이 약 0.1%라서 "정말 늘었다"고 봅니다.

**Q. 불량 위치는 어떻게 나눴나요? (O1)**
박스 중심점 `((x1+x2)/2, (y1+y2)/2)`을 구하고, 사진(1280×1024)을 가로·세로로 3등분한 9개 구역 중 어디에 속하는지 `pd.cut`으로 정했습니다.

### AI 활용

**Q. AI가 만든 코드에서 직접 고친 건 뭔가요?**
`loader.py`, `writer.py`, `main.py`에 각 단계가 무엇을 하는지 주석을 보강했고, README에 화면 캡처를 넣었습니다. 기능 로직은 테스트에서 문제가 나오지 않아 바꾸지 않았습니다.

테스트 중 나온 오류 2건은 AI에게 다시 맡겨 고쳤습니다.
- 결과가 0건일 때 이상 기록 함수에서 오류
- 산점도 축 표시 문제

자세한 내용은 [ai_usage_record.md](ai_usage_record.md)에 있습니다.

**Q. AI 결과가 맞는지 어떻게 확인했나요?**
처리 결과의 숫자를 원본 CSV에서 따로 센 숫자와 비교했습니다 (5,198건, 238건, 시설별 101 / 56 / 81건). 또 망가진 파일, 시설 0개 선택, 결과 0건 같은 극단적인 경우를 직접 넣어 시험했습니다.

## 7. 알려진 한계 (먼저 말하면 좋은 것)

- **불량코드표 오류는 건너뛰지 않음**: S4의 건너뛰기는 시설 로그에만 적용됩니다. 불량코드표가 없거나 깨지면 처리가 멈춥니다(이유는 6장 참고).
- **기간을 좁히면 급증 기준도 좁아짐**: Dash에서 날짜를 좁히면 "평소 불량률"도 그 기간 안에서만 계산됩니다. 하루만 고르면 비교할 날이 없어 급증이 감지되지 않습니다.
- **한글 글꼴 의존**: 맑은 고딕, AppleGothic, 나눔고딕 중 하나도 없는 환경(예: 기본 리눅스)에서는 그래프 한글이 깨질 수 있습니다.
- **이상 기록은 불량 종류 조건을 따르지 않음**: Dash의 이상 기록 표는 시설·날짜 조건만 적용합니다. 처리 지연 기록은 불량이 아닐 수도 있기 때문입니다.
